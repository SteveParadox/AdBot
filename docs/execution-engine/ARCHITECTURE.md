# Evidence-driven execution

AdBot runs directory collection inside its existing agent runner. Task preview identifies common intent categories and quantifiers. A deterministic directory route is available for simple exhaustive listing requests with no extra criteria or configured dataset. Broader requests still use the general planner, and an eligible listing task can start with the general planner until it reaches a recognizable directory.

The observer reads visible headings, marked categories, descriptions, conventional cards and repeated containers with accessible product links. Sampled semantic controls are bound to the current document. The runner chooses an observed directory route or a unique forward control, captures a batch, deduplicates stable product links, checks for repeat batches, and checkpoints coverage before dispatching the next action. Forward clicks run without a write grant. Navigation still goes through the controller, policy, DNS, robots and redirect checks. Assisted navigation uses the existing review gate.

A complete result requires a stable displayed total, unique coverage equal to that total, no detected filter or truncated batch, all records classified, and no enabled forward control. Visible category labels or direct descriptions can establish chatbot matches. Unknown records and conflicting categories keep the result partial. The output cites the observed directory page and the product link separately. A step limit, failed transition or interruption preserves checkpointed directory evidence. Existing job statuses stay compatible, with the result's `partial` flag and structured execution counters distinguishing partial from verified completion.

For model-driven work, known GPT-OSS providers estimate input from the serialized request bytes with margin. Unknown tokenizers retain the conservative byte count. The accounting reserves completion tokens separately and settles against provider usage when supplied. Use `ADBOT_AI_CONTEXT_WINDOWS` as a JSON map keyed by provider name or model ID to register deployment-specific windows. For example, `{"openrouter":32768,"my-local-model":8192}`. Requests outside a known window are skipped before dispatch. Budget diagnostics report the input estimate, output reserve, overall balance and primary fallback hold. Existing provider cooldown, retry and credential protections remain in use.

No migration is needed. Directory state is stored in the existing task checkpoint JSON and result JSON. API changes are additive. Restart the API and workers after deploying the feature to pick up the code and configuration.

## Boundaries

The route targets visible, bounded collections with interpretable totals and forward controls. It does not infer completeness from a search result, use private endpoints, or treat a broad AI tag as proof of chatbot status. Generic fuzzy field mapping, metadata-only discovery, exhaustive virtual-list traversal, cross-site search, and uncertain classification that requires inspecting detail pages are still on the general path or return partial. The deterministic record limit is 500. Deliberately misleading page totals or category labels require independent verification. Token estimates are not exact tokenizer counts, and missing provider usage remains estimated.

Full semantic observations remain available on the general route and for fallback. Directory collection uses a smaller action inventory and skips automatic screenshot capture when visual reasoning is off. General-route protection tracks repeated buttons and scrolling separately from transient element IDs, but it does not detect every possible cycle with arbitrary content changes. Existing circuit breaking is credential-scoped and ordered. This change does not add a separate latency-based router or dynamic provider discovery.
